## 1. Decision Statement

The Release Package Program establishes two **Visibility Surfaces** that translate registry metadata and watchdog flags into human-legible artifacts.

The governing principle is:

> **Registry metadata is for the watchdog. Visibility surfaces are for humans. The translation between them is one-way and lossy; humans should never have to read raw YAML to understand the federation.**

The Visibility Surfaces therefore:

- produce a **Registry Index Page** : a generated Markdown summary of every release, every compatibility relationship, every watchdog flag, and the current federation pin map;
- produce a **Release Note Compatibility Annex** : an auto-generated appendix attached to each catalog repo's release notes, listing compatibility claims, peer pins, asset inventory, and any open watchdog issues;
- are generated by a workflow on every registry update and on every watchdog run;
- live in `dea-release-package` and are consumed via GitHub Pages or as direct file references in each catalog repo's release pipeline.

The Visibility Surfaces do NOT:

- modify any registry manifest;
- modify any catalog repo's primary release notes (the annex is appended, never replacing);
- provide a real-time dashboard (the surfaces are point-in-time artifacts refreshed on the same cadence as the watchdog);
- introduce a new presentation framework (the surfaces are plain Markdown + a generated static site if Pages is enabled).

---

## 2. Why This Decision Is Necessary

The federation registry stores facts. The watchdog stores flags. Neither is human-legible at scale. Three irreducible gaps require visibility surfaces:

1. **Onboarding gap.** A new contributor who opens `dea-release-package/federation-registry/releases/2026/09/` sees 200 YAML files. They need a 1-page summary.

2. **Release note gap.** A catalog team ships a release with peer pins, compatibility claims, and asset inventory. The release notes carry prose, not the structured facts. Consumers re-derive the facts by reading the registry.

3. **Federation health gap.** The watchdog opens 30 issues over a quarter. No one looks at the issues directly. A quarterly summary surfaces the patterns.

---

## 3. Decision Drivers

The Visibility Surfaces address:

1. **Onboarding** : a new contributor understands the federation in one page;
2. **Release note integration** : compatibility metadata travels with each release;
3. **Quarterly reporting** : release coordination meetings have a real artifact;
4. **Federation health summary** : pin map, compatibility state, watchdog activity at a glance;
5. **Single source of truth for humans** : one path for "what does the federation look like right now";
6. **Append-only discipline** : visibility surfaces are generated; humans never edit them;
7. **No new presentation framework** : Markdown and (optional) GitHub Pages only.

### 4.3 Generation

Triggered on every merge to `main` in `dea-release-package` (i.e. after every registry PR merge and after every watchdog run).

```yaml
# dea-release-package/.github/workflows/visibility.yml
name: Visibility Surfaces

on:
  push:
    branches: [main]
    paths:
      - 'federation-registry/**'
      - 'toolkit/src/dea_release_package/visibility/**'
  workflow_dispatch:

jobs:
  index:
    runs-on: ubuntu-latest
    steps:
      - checkout (fetch-depth: 0)
      - setup python
      - run: python -m dea_release_package.visibility.index --output federation-registry/README.md
      - run: git diff --quiet federation-registry/README.md || git add ... && git commit -m "chore(visibility): regenerate registry index" && git push
```

### 5.3 Generation

The catalog repo's `publish-versioned.yml` adds a step:

```yaml
- run: python -m dea_release_package.visibility.annex \
    --repo ${{ github.repository }} \
    --tag ${{ github.ref_name }} \
    --release-notes out/${{ github.ref_name }}/release-notes.md \
    --annex-out out/${{ github.ref_name }}/compatibility-annex.md
- run: cat out/${{ github.ref_name }}/compatibility-annex.md >> out/${{ github.ref_name }}/release-notes.md
```

The annex is regenerated at build time; it is not committed separately. The catalog repo's existing `release-notes.md` is the human-authored part; the annex is appended after.

## 6. Optional: GitHub Pages Site

If `dea-release-package` has GitHub Pages enabled, the visibility workflow additionally generates a static site at `https://technehub-labs.github.io/dea-release-package/` with:

- The Registry Index Page (rendered as HTML);
- Filterable release tables (per repo, per quarter, per pin);
- Watchdog issue summaries;
- Quarterly timeline as a graph (Mermaid rendered to SVG);
- Compatibility state visualisations (matrix heat-map per release).

The site is a thin static rendering of the same data. No new presentation framework is introduced; GitHub Pages + a static-site template (Jekyll default, or MkDocs if the org uses it) is sufficient.

Whether to enable Pages is deferred to a future CR.

## 7. The Visibility Toolkit Module

`dea-release-package/toolkit/src/dea_release_package/visibility/` exposes:

| Module | Purpose |
|---|---|
| `index.py` | Registry Index Page generator. |
| `annex.py` | Release Note Compatibility Annex generator. |
| `models.py` | Pydantic models for index rows, annex tables, severity counts. |
| `templates/` | Markdown templates (Jinja2). |

Tests cover:

- Index generation against a populated registry;
- Annex generation against a single release's manifest;
- Severity count aggregation;
- Quarterly summary computation.

---

## 8. Failure Modes and Mitigations

| Failure mode | Mitigation |
|---|---|
| Index generation fails on a malformed manifest | Generator asserts all manifests parse against `registry-schema@v1`; failures open a critical watchdog issue. |
| Annex references a missing peer release | Annex shows "⚠️ target release not found in registry"; the underlying watchdog issue is `cross-version: missing peer`. |
| Index regeneration races with a registry PR merge | The visibility workflow uses GitHub's serial job queue per repo branch; concurrent runs are rejected. |
| Annex contradicts the catalog repo's own release notes | Annex is a generated appendix; the human-authored prose above it takes precedence in disputes. The annex is data, not narrative. |

---

## 9. Consequences

### Positive

- New contributors onboard in one page.
- Compatibility metadata travels with every release, not just the registry.
- Quarterly release coordination meetings have a real artifact.
- The federation has a public face.

### Negative

- Generated artifacts (`federation-registry/README.md`) are committed to git; every push generates a commit. The history is noisy if not batched.
- The annex's "Mandates from peer releases" section may surface contradictions the catalog team wasn't aware of.
- GitHub Pages (if enabled) is a new public surface that the program must keep aligned with the registry.

---

## 10. Rejected Alternatives

### A : Real-time web dashboard

A Flask/FastAPI app querying the registry live.

Rejected because:

- Introduces a runtime dependency.
- Doesn't fit OpenDEA's "everything is a CR, everything is a commit" discipline.
- A static generated site is good enough.

### B : Per-catalog visibility page

Each catalog repo has its own visibility page generated from the registry.

Rejected because:

- Duplicates effort.
- The federation view cannot live in any single catalog repo.

### C : Hand-curated README

Humans maintain `federation-registry/README.md`.

Rejected because:

- Drift from reality within hours of any registry update.
- Doesn't scale.

### D : Inline release-note authoring

Catalog teams manually write compatibility claims into release notes.

Rejected because:

- Already happens (the prose part of release notes); the annex adds the structured facts.
- Manual authoring of structured facts invites drift.

---

## 11. Explicit Non-Decisions

This CR does NOT decide:

- Whether GitHub Pages is enabled (deferred);
- The exact static-site template (Jekyll default unless the org uses MkDocs);
- Whether the annex is included in `release-notes.md` or as a separate file (decision: appended, included in the same file; the catalog repo's choice);
- The cadence of the "release coordination report" PR (deferred; default quarterly).

---

## 12. Decision Summary

The Visibility Surfaces:

- produce a generated Registry Index Page (`federation-registry/README.md`);
- produce an auto-generated Release Note Compatibility Annex appended to each catalog release;
- are point-in-time, generated on registry updates and on watchdog runs;
- are plain Markdown + (optional) GitHub Pages; no new presentation framework;
- are read-only; humans never edit generated artifacts.

The surfaces make the federation legible to humans without sacrificing the registry's discipline.
